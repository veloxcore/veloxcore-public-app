faqSub: "Questions we get on almost every RAG discovery call."
faqs:
  - q: "How do you choose chunk size and overlap?"
    a: "Chunk size is a function of your document structure and query patterns. For narrative documents (contracts, policies), we typically use 512–1024 token chunks with 15–20% overlap. For structured documents (tables, product specs), we often use smaller chunks or preserve table structure as atomic units. We always run retrieval quality experiments on 50+ representative queries before committing to a strategy."
  - q: "What if our documents change frequently?"
    a: "We set up event-driven re-indexing via Azure Blob Storage triggers — when a document is updated, the affected chunks are automatically re-ingested and the stale vectors replaced. For high-velocity document sets, we can configure near-real-time indexing. The LLM layer always queries the current index state."
  - q: "How do you handle access control — different users seeing different documents?"
    a: "Azure AI Search supports security filters that enforce document-level access control at query time. We tag each chunk with the access groups that can see it, and every retrieval query includes a filter that limits results to chunks the requesting user is authorised to access. This is enforced server-side — it's not possible to retrieve unauthorised chunks by manipulating the query."
  - q: "What document formats can you ingest?"
    a: "PDF, Word, PowerPoint, Excel, HTML, plain text, and markdown natively. For scanned PDFs and images, we use Azure Document Intelligence (Form Recognizer) for OCR. For structured data in databases, we build custom extraction pipelines that convert rows into text chunks. We've ingested everything from 40,000-page legal corpora to real-time database tables."
