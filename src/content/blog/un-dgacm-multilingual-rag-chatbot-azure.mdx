It is 11:30 PM in New York. A senior UN staff member is drafting remarks for a General Assembly session that opens in eight hours. She needs the exact language from a 2003 Security Council resolution, in Arabic, cross-referenced against how member states voted. The document repository holds hundreds of thousands of files. The voting database is a separate system. Neither speaks to the other, and neither understands a natural language question.

This is the problem the UN Department for General Assembly and Conference Management set out to solve — and how they solved it is a practical blueprint for any organization drowning in institutional knowledge.

<h2 id="scale">The scale problem</h2>

**DGACM** is the UN organ responsible for managing documentation services across all principal UN bodies. Its output spans General Assembly resolutions, Security Council decisions, committee reports, verbatim records, and official correspondence — accumulated across decades, in six official languages: English, French, Arabic, Spanish, Russian, and Chinese.

The **Official Document System (ODS)** holds this corpus. It is invaluable and effectively unsearchable at speed.

Traditional keyword search fails in two ways here. First, a query for "peacekeeping financing" in English will not surface the equivalent Arabic or Chinese documents unless the user knows the precise terminology in each language. Second, voting records — how each member state voted on each resolution — lived in a SQL Server database that had no connection to the document corpus. Answering "How did the P5 vote on Resolution 2334?" required manually consulting two separate systems and synthesising the result.

The multilingual constraint is not optional. The six UN official languages are a constitutional requirement. Any solution that treated them as a translation problem rather than a retrieval problem was a non-starter.

<h2 id="agents">Two agents, one interface</h2>

Rather than building a single general-purpose assistant, DGACM deployed two focused agents behind a shared interface.

**DGACM Mini** is the primary agent for staff and delegates. It handles queries about ODS documents and voting data across all six languages. It is the system a researcher uses at 11:30 PM to find that Arabic resolution and check the vote record in the same conversation turn.

**Athena Help Assistant** is scoped to DGACM's internal Athena documentation system. Staff seeking guidance on internal processes get immediate, sourced answers without touching the main document corpus. The separation keeps knowledge domains clean and retrieval precise.

Both agents are accessible through **LibreChat**, an open-source ChatGPT-style frontend that DGACM customised for its needs. Users interact the same way they would with a knowledgeable colleague: ask a question in natural language, in their preferred language, and get a grounded answer with source references attached.

> The architectural decision to separate agents by knowledge domain rather than by user type is what keeps retrieval precise. A general-purpose assistant over everything produces answers that sound right but cite the wrong document. Focused agents do not.

<h2 id="multilingual">Multilingual by design</h2>

The centrepiece of the system is how it handles the six official languages. Each language has its own dedicated **Azure AI Search index**, populated with vector embeddings generated by Azure OpenAI's `text-embedding-3-small` model. When a query arrives, the agent identifies the appropriate language context and routes retrieval to the correct index.

This is not translation. A question asked in Arabic is embedded and searched against the Arabic document corpus. The retrieved chunks are in Arabic. The model synthesises a response in Arabic. The precise terminology of UN documents in their original language is preserved throughout.

Retrieval inside each index uses **semantic hybrid search**: dense vector similarity via an HNSW index combined with sparse keyword matching, then scored by Azure's semantic reranker on a 0–4 scale. Results below a configurable threshold are filtered before reaching the language model. This two-stage approach catches documents that keyword search misses and eliminates low-confidence results that a pure vector search might surface.

<h2 id="architecture">Under the hood</h2>

The backend is a **FastAPI** application running Python 3.13, structured around a multi-agent orchestration layer built with **LangGraph**. Agent instantiation is handled by an `AgentFactory` that maps an `AgentType` enum to a concrete agent class.

Three agent types are registered:

- `chatbot` maps to `ChatbotAgent` — equipped with language-specific RAG tools for all six indexes plus the voting data tool
- `helpassistant` maps to `AssistantAgent` — RAG tools pointed at Athena document indexes
- `title_generator` maps to `TitleGeneratorAgent` — a lightweight agent that generates conversation titles after the first message using GPT-4o-mini with minimal context

Each agent is a **LangGraph graph** compiled and invoked per request. The **ReAct** (Reasoning + Acting) pattern lets each agent reason about which tools to invoke, execute retrievals iteratively, and synthesise a final response — rather than following a fixed retrieval pipeline. This matters when a query spans both document content and voting records: the agent reasons about which tools to call and in what order, not a hardcoded sequence.

The **VotingDataAgent** translates natural language voting queries into parameterised SQL, executes them against the SQL Server database, and returns structured results that the main agent weaves into its response alongside document context.

Two middleware layers protect every request. `AuthMiddleware` validates an API key header on all protected endpoints. `RequestAuditorMiddleware` runs a PII detection pipeline with a configurable sensitivity threshold (default 70/100), flagging or rejecting queries that contain personally identifiable information before they reach the language model. Both are required for a system operating within UN security standards.

Answer quality is measured continuously using **Azure AI Foundry**, tracking four dimensions per response: relevance, coherence, groundedness, and intent resolution. Both positive and negative evaluation datasets are maintained to test the system against answerable and unanswerable queries. The team can detect quality regressions as indexes are updated and models change — before users encounter them.

**Technical stack at a glance:**

| Layer | Technology |
|---|---|
| Backend | FastAPI, Python 3.13+ |
| AI Orchestration | LangChain 0.3.26+, LangGraph 0.5.4+ |
| Language Model | Azure OpenAI, GPT-4o-mini |
| Embeddings | Azure OpenAI, text-embedding-3-small |
| Vector Search | Azure AI Search (HNSW, semantic hybrid) |
| Frontend | LibreChat (React 18, Vite, TailwindCSS) |
| Voting Database | SQL Server, pyodbc / SQLAlchemy |
| Evaluation | Azure AI Foundry |
| Deployment | Azure DevOps CI/CD |

<h2 id="outcomes">What it delivers</h2>

The shift is not incremental. Staff and delegates no longer need to know which document to look for or where. A question asked in any of the six UN official languages surfaces the most relevant documents from the correct language corpus in seconds, with source references attached.

Queries that once spanned two separate systems, two sets of credentials, and manual synthesis now resolve in a single conversation turn. A delegate checking how the five permanent members voted on a specific resolution gets the voting record and the relevant document context together.

The Athena Help Assistant has absorbed a class of support queries that previously required human intervention, freeing support staff for higher-value work.

The modular architecture means growth does not require rearchitecting. A new document collection connects to a new Azure AI Search index and a new agent tool. A new specialised assistant registers in the factory. The infrastructure scales alongside DGACM's evolving needs.
